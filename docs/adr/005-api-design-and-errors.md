# 005. Admin API design and error responses

- **Status:** Accepted
- **Date:** 2026-11-26

## Context
The admin API (first resource: monitored sites) is consumed by the dashboard and must have a stable contract, correct status codes and predictable error bodies, while the database schema keeps evolving.

## Decision
- **DTOs are Java records, separate from JPA entities.** Requests (`CreateSiteRequest`, `UpdateSiteRequest`) contain only client-settable fields; responses (`SiteResponse.from(entity)`) choose exactly what is exposed. Server-generated fields (`id`, `publicKey`, `createdAt`) cannot be set by the client.
- **Layers:** controller (HTTP, validation, status codes) → service (business rules, transactions, DTO ↔ entity mapping) → repository. The entity never leaves the transaction, which matters with `open-in-view=false`.
- **Bean Validation** on request records (`@Valid`), including container elements (`Set<@NotBlank String>`).
- **`PUT` is a full replacement** with the same constraints as create; `PATCH` is postponed until the dashboard needs partial updates.
- **Status codes:** `201` + `Location` on create, `200` on read/update, `204` on delete, `400` on invalid input, `404` on unknown id, `409` on a duplicate site name (case-insensitive, after trimming), `401`/`403` from security (ADR 001).
- **Errors use `ProblemDetail` (RFC 9457)** everywhere (`spring.mvc.problemdetails.enabled=true` plus a global `@RestControllerAdvice`).
- **Database constraint violations are mapped by constraint name:** only `uq_site_name_ci` (two concurrent requests with the same name passing the application check) becomes `409`; any other `DataIntegrityViolationException` is logged and returned as a generic `500`, because it means a bug slipped past validation.
- **Identifiers:** UUIDs generated by Hibernate on persist; timestamps as `Instant` in `timestamptz` columns, rendered in UTC.
- **API documentation** with springdoc-openapi; the generated OpenAPI spec will be used to generate the dashboard's TypeScript types.

## Alternatives considered
- **Exposing entities directly:** mass assignment of server-owned fields, lazy-loading and serialization problems, schema changes leaking into the contract.
- **`Optional` fields for partial updates:** `Optional` is meant for return values; nullable fields or a separate `PATCH` DTO are clearer.
- **Mapping every `DataIntegrityViolationException` to `409`:** hides bugs (a violated `CHECK` or `NOT NULL` would look like a client conflict).
- **MapStruct:** unnecessary while mapping is a few static `from` methods.

## Consequences
- Fields are declared twice (entity and DTO): some duplication in exchange for an independent contract.
- The handler must know the names of the constraints it maps; renaming an index requires updating the handler.
- Every status code above is covered by end-to-end tests (`SiteApiTest`).
